# SaaS blueprint — the parts every paid, multi-user product needs

Added in 1.1.0 (18 Nov 2026). "build me a SaaS" must not mean re-inventing accounts, tenants, billing, admin and email on every project — and must never mean shipping one without them. When the plan says the product has **paying customers or organizations as customers**, `/pf-plan` works through this list with the user and `/pf-build` writes each chosen block into the SPEC (screens, data model, routes, a `feature-` diagram each, acceptance checks). It is a checklist of decisions, not code: the stack stays whatever the plan locks, and every block is built to the existing contracts. A block the product does not need is recorded as "not needed — <reason>", never silently dropped.

| Block | The decision to make at plan time | What the SPEC must then carry |
|---|---|---|
| **1. Tenancy** | Who is the customer: a person, or an organization with members? | *Organization:* `organizations`, `memberships` (role), every tenant-owned table has `org_id`, and the access policy isolates by **membership of the org**, not by user id. The isolation test (`security.md` B) is run **across two organizations**, not just two users. |
| **2. Roles** | Which roles exist (owner / admin / member / read-only) and what each may do | A permission table in the Brief; every route's auth line names the minimum role; a test per role boundary. |
| **3. Billing** | Free, trial, plans, per-seat or usage? Which provider (Stripe by default; a merchant-of-record — Paddle, Lemon Squeezy — when sales tax/VAT handling should be theirs)? | Provider-hosted checkout and customer portal (card data never touches our server); a **signature-verified, idempotent webhook** as the only writer of subscription state; a `subscriptions` table; the plan read from our database, never trusted from the client. Provider fees are per-transaction — stated in the budget forecast. Built and tested in the provider's **test mode** only; live keys are set by the user at go-live. |
| **4. Plans and limits** | What does each plan allow? | One `plans` definition (limits, features) in code; limits enforced **server-side** on the route, with a clear upgrade message; a test per limit. |
| **5. Lifecycle email** | Which emails must go out (verify, reset, invite, receipt, trial ending, payment failed)? Which sender (the auth provider's built-in for auth mail; Resend/Postmark/SES free tier for the rest)? | Templates with verbatim copy in the SPEC; a sending domain with SPF/DKIM/DMARC set up in `/pf-setup` (the user adds the DNS records); no marketing mail without consent (`compliance.md`). |
| **6. Admin back-office** | What must the operator do without a developer: see customers, change a plan, refund, disable an account, impersonate for support? | An `/admin` area behind the admin role, `noindex`, rate-limited; every admin action written to an **audit log** (who, what, when); impersonation, if built, is visibly bannered and logged. |
| **7. Account lifecycle** | Trial end, failed payment (grace period), downgrade, cancel, delete | A state diagram (`feature-subscription-lifecycle`); data export and deletion on request (`compliance.md`); what happens to an organization's data when its owner leaves. |
| **8. Onboarding** | What is the first-run path to the product's first value? | The `app-journey` diagram starts at sign-up and ends at that first value; its e2e test is the product's smoke test. |

## Rules
- **Nothing here unlocks a paid tool by itself** — the cost posture holds; a provider with fees is chosen on a stated price and a yes.
- **Money paths are data-sensitive.** A product that takes payments is planned as `data_sensitivity: high` unless the user says otherwise in words, and its webhook, plan-enforcement and tenant-isolation tests are part of `verify`.
- **No live charge is ever made by the factory.** Test mode in build, harden and e2e; the switch to live keys is the owner's step at go-live.
