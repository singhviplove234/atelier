# Languages and regions — locale-ready always, translated only when asked

Added in 0.4.0. A product for more than one country or language must not need a rewrite to get there, and a single-language product must not carry translation machinery it does not use (`code-simplicity.md`). So there are two levels, chosen at plan time by the Brief's `Locales:` line (default: one locale, e.g. `en-US`).

## A. Always — even with one locale (cheap, and it is what makes level B possible later)
1. The document declares its language (`<html lang>`), and the charset is UTF-8 end to end (pages, database, exports).
2. **Dates, times, numbers and money go through the platform's locale formatter with an explicit locale** (`Intl.DateTimeFormat`, `Intl.NumberFormat`, or the stack's equivalent) — never hand-built strings like `"$" + n` or `dd/mm/yyyy` concatenation. This is what gets Indian digit grouping (`1,00,000`), `₹` vs `$`, and day-month order right without special cases.
3. Times are stored in UTC and shown in the viewer's zone; money is stored as an integer minor unit plus an ISO currency code, never a bare float.
4. No sentence is assembled by joining fragments around a variable ("You have " + n + " items") — one full sentence per string, with a placeholder, so it can be translated and pluralized later.
5. Layout survives text 30% longer than the source copy and names/addresses that are not Western-shaped (one name field is allowed; postcode and state are not assumed).

## B. Only when the Brief lists more than one locale
1. **One message catalog per locale** using the stack's standard i18n library (never a hand-rolled one); every user-facing string, including errors, emails, alt text and metadata, comes from it. The source locale is the SPEC's verbatim `Copy:`.
2. **Translations are supplied, never invented as final.** The SPEC carries each locale's copy. Where the user has not supplied a translation, Claude drafts it and marks the catalog entry `needs-review`; a build with `needs-review` strings passes, a **go-live does not** until the user says the translations are reviewed. Legal pages (privacy, terms) are never machine-translated as final — flagged "needs legal review" (`compliance.md`).
3. **Routing and discovery:** locale in the URL (`/en/…`, `/hi/…`), a visible language switcher that keeps the user on the same page, `hreflang` alternates and an `x-default` on every page, one sitemap entry per locale (`seo-ai-visibility.md`), and no automatic redirect that hides a locale from crawlers.
4. **Plurals, gender and direction** through the library's message format (ICU) — and when a right-to-left locale is listed, logical CSS properties (`margin-inline-start`, not `margin-left`) and `dir` set per locale.
5. **Formats per locale**, not per deployment: the same user can see `en-IN` money and `en-US` dates only if the Brief says so.

## C. Checks (the builder's gate)
Always: no user-facing date, number or currency formatted without a locale; `lang` set; no concatenated sentences (lint rule or review). Multi-locale only: every key exists in every locale (a missing key **fails**, it never falls back silently in production); `hreflang` and per-locale sitemap entries present; the `app-journey` e2e test passes in **every** locale; a pseudo-locale run (accented, 30% longer) shows no clipped or overlapping text on any screen; count of `needs-review` strings reported. Any miss → `failures: i18n: <check>`. The result carries `i18n: <n> locales, <k> needs-review`.
