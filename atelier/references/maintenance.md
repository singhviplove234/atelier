# Maintenance & backups — the factory keeps a live product healthy, patched and recoverable

Standing requirement: Phase 3. After launch the factory does not walk away — it acts as **production support / a maintenance role**: it keeps dependencies patched and secure, keeps the product within its contracts over time, and makes sure the code and data are backed up **and that a restore actually works**. Run by `/pf-maintain`, on a schedule the user approves or on demand. Free-first and minimal; it **proposes**, it never silently changes a live product.

## A. The maintenance loop (recurring — proposes; never auto-ships for sensitive)
On each run, against the live project, on a `maintenance/<date>` branch:
1. **Dependencies & security advisories.** `npm outdated` + `npm audit` + `osv-scanner`; list what is behind and what has a known vulnerability. Apply **safe** updates (patch/minor + lockfile); hold majors for a human note with the reason.
2. **Re-run the contracts on the live site.** A light `/pf-harden` re-check (perf budget, SEO, security headers/RLS, a11y) to catch drift since launch; open fixes on the branch.
3. **Certificates & host limits.** TLS cert not within 14 days of expiry (ties to `monitoring.md`); host plan limits not about to bite (the `limits` check).
4. **Backups healthy (section C).** Confirm backups ran and, periodically, run a **restore drill**.
5. **Secret hygiene (section E).** Flag any tracked secret older than its rotation cadence and any that should be retired (a departed collaborator, a leaked or over-scoped key); prepare the guided rotation — Claude never types or stores the secret, it walks the user through the provider page and updates the env-var **name** only.
6. **Spend vs forecast (section F).** Read the real month-to-date bill (or free-tier usage) for each provider the project uses, compare it to `planning.budget_forecast` and to the free-tier limits, and flag drift toward anything billable **before** it bills — recommend-only.
7. **Open a PR; do not auto-merge for sensitive.** The run opens one `maintenance/<date>` PR with the code/dependency fixes above. Secret rotations and spend findings are **not** code changes — they are reported to the user as actions/alerts, never committed. For a `data_sensitivity: high` project the PR **waits for the user's review and merge**, then the normal deploy (which brings auto-rollback). For a low-stakes internal/marketing site the user may pre-authorize auto-merge of **safe** updates (patch/minor, green tests); majors and anything that fails a contract always wait.

## B. Scheduling (allowed for maintenance — never for the pentest)
Maintenance may run on a schedule the user sets (e.g. weekly), via the scheduled-task tools, **because it only proposes** (a PR): it never deploys or merges a sensitive project on its own, and it is **not** the pentest (the pentest is never scheduled, never `--go`). A scheduled run that finds nothing says so quietly; one that finds something opens the PR and alerts the user. The user can change or stop the schedule anytime.

## C. Backups & restore — where the code and data live, and proof a restore works
This is the backup plan the factory follows:
- **Code → GitHub (authoritative).** The repo on GitHub **is** the code backup: full source + history, off your machine. Your local `<code root>/<slug>` is a working copy; the deploy builds from the repo. A second mirror remote is optional. So code is backed up by design — nothing extra to set up.
- **Data → Supabase automated backups + a free off-Supabase copy.** Supabase takes **automated daily backups** (free tier keeps **~7 days**; paid tiers add longer retention and point-in-time recovery). For longer retention or a copy **outside** Supabase, free-first: a scheduled **`pg_dump` logical backup to Azure Blob Storage** (cool tier — pennies, effectively free at small size), e.g. weekly, kept N weeks — set up via `/pf-setup backup`. Uploads in Supabase Storage are covered by Supabase's own backups; add them to the dump only if the project needs it.
- **Restore is tested, not assumed.** `/pf-maintain` periodically runs a **restore drill**: restore the latest backup into a **scratch** database and verify it loads and the app can read it — because "a backup exists" is not "a restore works." The documented restore step lives in the repo README (ties to `security.md` A13).
- **Retention & privacy.** Keep enough history for the project's risk (a client-data product keeps more than a hobby site). A backup of data with personal information is handled under `compliance.md` (access-controlled, not shared, deletable on request). **Never back up secrets** — they live in env vars / Key Vault, never in the dump.
- **Recommend-only on cost.** Supabase daily backups and GitHub are free; the Blob dump is effectively free at small size. A paid backup tier (Supabase PITR, large retention) is proposed only when the project's real recovery needs force it, with the price + a yes.

## E. Secret hygiene & rotation — keys don't live forever, and the factory never holds them
A live product's secrets (database service keys, deploy tokens, API keys, the Blob connection string, a `GITHUB_TOKEN`) need **rotating on a cadence**, and **retiring immediately** when a collaborator leaves or a key is leaked or over-scoped. The factory treats this as maintenance, under one unbreakable rule carried from `security.md`: **Claude never sees, types, pastes or stores a secret value** — it only ever knows the env-var **name**. So rotation is guided, not automated:
- **Track, don't keep.** The factory records, per project, each secret's **name**, where it lives (the provider + the env var / Key Vault entry), its **owner/scope**, and the date it was last rotated — **never the value**. This lives in `factory.json.maintenance.secret_rotation` (names + dates only).
- **Cadence, provider-agnostic.** Default rotation targets: **deploy/API tokens every 90 days**, **database service keys every 180 days**, and **immediately** on a leave/leak/over-scope event — the same cadence across every provider (Azure, AWS, GCP, Supabase, GitHub, Vercel…). A project may set a stricter cadence; a `data_sensitivity: high` project rotates on the shorter end and on every access change.
- **Guided rotation (the only way).** When a secret is due, `/pf-maintain` opens the provider's key page in Chrome, tells the user exactly which key to regenerate and which scope to grant, waits while **the user** generates and copies it, then updates the **env var by name** on the host (prefilling the name, never the value) and records the new rotation date. The old key is revoked **after** the new one is confirmed live by a health check, so nothing breaks mid-rotation. Key Vault / provider secret stores are preferred over raw env vars where the host offers them (rotation there is a version bump, no redeploy).
- **Never:** store a secret in `factory.json`, a doc, a commit, a backup or a reply; rotate a key Claude cannot confirm the user controls; or revoke the old key before the new one is verified.

## F. Spend — the real bill, not just the forecast
The forecast (`/pf-plan`) says what a project *should* cost; maintenance checks what it *actually* costs, so a free-first project never quietly slips into a bill. On each run, per provider the project uses:
- **Read the real number where a tool exists.** Azure has cost/billing tools (read month-to-date actuals and the forecast directly); for a provider with no tool wired, `/pf-maintain` opens that provider's billing/usage page in Chrome, reads the month-to-date figure and the free-tier usage, and records it. It never needs a payment method to *read* a bill.
- **Compare to three lines:** the project's `planning.budget_forecast`, **$0** (the free-first baseline), and each free tier's **limit** (e.g. Supabase row/egress caps, a static host's bandwidth, function invocations). Flag when usage crosses ~80% of any free-tier limit, or when actual spend appears above the forecast.
- **Recommend-only, quality never traded.** A spend alert is an alert, not an action: the factory reports the number, what is driving it, and the cheapest option that still clears the project's quality/security bar (`cost-posture.md`, `recommendations.md`) — it never downgrades the product to dodge a bill, and never creates or changes anything billable without the user's yes. Record the latest reading in `factory.json.maintenance.spend` (numbers + date, no payment details).

## D. How it is invoked
`/pf-maintain <slug>` runs one pass now; `/pf-maintain <slug> --schedule weekly` sets the recurring schedule; `--check` reports when it last ran, what is pending, the backup/restore status, **which secrets are due for rotation, and the latest spend-vs-forecast reading**. It writes `factory.json.maintenance` and logs each run. The growth side is `/pf-grow` (`references/growth.md`). A product in this phase runs the **kanban** methodology (`planning.md`).
