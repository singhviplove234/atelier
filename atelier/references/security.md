# Security contract — every Atelier product is built secure by default and checked like a defensive review

Standing requirement: every product the factory ships is secure by default — security is built in, never bolted on. This file is the contract. The builder implements section A on every build and must pass section C before `status: ok`; `/pf-harden` pass `security` re-checks the live site. Scope is strictly **defensive and self-only**: inspecting and fixing your own code and your own deployment. No attack tooling, no scanning of anything you do not own, no autonomous exploitation. For a formal penetration test before a major launch, brief a human tester with a signed scope (the optional `/pf-pentest` stage covers your own pre-production).

## A. Build rules (do by default, not when asked)

1. **Data access.** Every Supabase table has Row Level Security **enabled** with policies that scope rows to `auth.uid()` (or a documented public-read policy for truly public data). No table without a policy. The service-role key is used only in server code and never shipped to the browser. Each migration that creates a table also creates its policies.
2. **Authentication.** Supabase Auth only (email/password with confirmation, magic link, or OAuth providers the SPEC names). No home-made password handling. Sessions via `@supabase/ssr` cookies (`HttpOnly`, `Secure`, `SameSite=Lax`). Password reset and email change go through Supabase flows. Admin areas require an explicit `role = admin` claim check on the server, not a hidden link.
3. **Input.** Every route handler and server action validates its input with zod (types, lengths, enums, allow-lists) and rejects anything else with 400. Output is escaped by React by default; never use `dangerouslySetInnerHTML` with user content. Database access only through the Supabase client or parameterised queries, never string-built SQL.
4. **Rate limits and abuse.** Login, signup, password reset, contact/lead forms, and any route that sends email, spends money or calls a paid API are rate-limited (per IP + per account; the host's/edge limiter or a small token bucket in the database, no paid service). Forms get a honeypot field plus Turnstile/hCaptcha free tier **only if** the Brief asks; never a paid captcha.
5. **Headers** (set in `next.config` `headers()` or `middleware.ts`): `Content-Security-Policy` (nonce-based scripts, `frame-ancestors 'none'`, `object-src 'none'`, explicit `connect-src` for Supabase/analytics), `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` denying camera/microphone/geolocation unless used, `X-Frame-Options: DENY`. HTTP → HTTPS redirect at the host.
6. **Secrets.** Only environment variables; `.env*` in `.gitignore`; `.env.example` lists names only; `NEXT_PUBLIC_` prefix only for values that are safe in the browser (anon key yes, service role never). A secret scan (`gitleaks` or `trufflehog` filesystem mode) runs on the repo at build and fails on any hit.
7. **Dependencies.** `npm audit --audit-level=high` clean (fix or override with a written reason); lockfile committed; no packages with install scripts from unknown publishers; Dependabot or `npm outdated` noted in the harden report.
8. **Uploads and files.** Type allow-list by magic bytes (not extension), size cap, random object names, stored in Supabase Storage with bucket policies, served from the storage domain (never executed from our origin), images re-encoded through `sharp`.
9. **Payments and webhooks.** Webhook signatures verified (Stripe/Razorpay), idempotency keys on write operations, amounts computed server-side only.
10. **Errors and logs.** Custom `error.tsx`/`not-found.tsx`; stack traces and SQL never shown to users; logs never contain passwords, tokens, card numbers or full personal records; `console.log` of request bodies removed before build.
11. **Crawl and exposure.** `/api/*`, `/admin*`, preview and staging deployments are `noindex` and disallowed in robots; source maps not served in production; `/.env`, `/.git`, `/server-status`-style paths return 404 (the host handles this; the health check confirms it).
12. **Cookies, privacy, consent.** Only essential cookies before consent; analytics loaded after consent (and after interaction, per the performance budget); a privacy page that states what is collected; data deletion path for user accounts (Supabase `auth.admin.deleteUser` + cascading FKs).
13. **Backups and recovery.** Supabase daily backups (free tier: 7 days) confirmed; a documented restore step in the repo README; migrations reversible where possible.
14. **Least privilege on the host.** Deploy tokens scoped to the one project; Azure resources in a per-project resource group; no shared admin credentials in the pipeline (see `pf-setup` hard rules).
15. **Gated checks before merge (data-sensitive projects).** For a project handling client, financial or personal data (data-sensitive, `brief.data_sensitivity: high`), the security checks — secret scan, `npm audit`, and the section-B tests (RLS proof, auth walls, validation, headers, rate limit) — run as a gate on every push so nothing merges unchecked. This is free on a **self-hosted** GitHub Actions runner (own hardware, $0 today — see `cost-posture.md`); where a hosted runner would bill minutes, run the same gate as a local pre-push hook instead. Lower-sensitivity projects may rely on the in-session `/code-review` + `/security-review` pass; the gate is the add-on that makes it enforced, not advisory.

## B. Tests the builder writes (part of the safety net)
- **Adversarial edge cases (every key user flow — sign-up, login, payment, any write):** before building the flow, list the top 5 ways a real user would break it (double-click, retry on a slow network, two users at once, back button mid-action, malformed/oversized input) and write a test for each. Money/stock-changing writes carry an idempotency key so a repeated request is a no-op; the test fires the same request twice and asserts one effect.
- **RLS proof:** sign in as user A, create a row; sign in as user B, attempt to read/update/delete it → must fail; anonymous attempt → must fail. One test per table with user data.
- **Auth walls:** every protected route returns 401/redirect when signed out; admin route returns 403 for a non-admin.
- **Validation:** each API route rejects an oversized/malformed body with 400.
- **Headers:** a request to `/` carries every header in A5.
- **Rate limit:** the 11th login attempt in a minute from one client is rejected.

## C. How it is checked (build step 6 and `/pf-harden` pass `security`) — read-only against your own deployment
1. Section B tests pass.
2. `npm audit --audit-level=high` → 0; secret scan → 0 hits; `git log -p` grep for obvious key patterns → 0.
3. Static check: `eslint-plugin-security` + Next.js lint clean; grep for `dangerouslySetInnerHTML`, string-built SQL, `NEXT_PUBLIC_` on a server secret, `service_role` in client bundles (`.next/static`) → 0.
4. Live (`curl -sI` on `live_url` and 3 deep routes): HTTPS redirect, HSTS, CSP, nosniff, referrer, permissions, frame headers all present; certificate valid > 14 days; `/.env`, `/.git/HEAD`, `/api/health` (if present) behave as expected; `robots.txt` disallows `/api/` and `/admin`.
5. Supabase (via CLI/SQL with the project's own credentials): every table in `public` has `rowsecurity = true` and >= 1 policy; no `anon` grants on tables that hold user data; storage buckets private unless the SPEC says public.
6. A plain-language report: table of checks (check | result | fixed on branch / needs the user) and a short "what a human pentester should still look at" list when the product handles payments, health data or more than one tenant.

Never: run a scanner or test against any host other than `live_url` / `<local>` of this project; attempt to bypass auth of a live system beyond the section-B tests on test accounts; store or print credentials found during the scan (report the path only); create paid security services.
