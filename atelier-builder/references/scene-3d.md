# 3D product scene — an interactive model of the product, built to the speed budget (optional)

Added in 0.5.0. An option (`options.md`): offered for a brand or product page where the product's physical form is what sells it — furniture, a device, a watch, packaging — and never added by default. It is for **web** pages; a native mobile app's 3D is a platform matter and is not covered here. Recorded as `options.scene_3d`: `none` (default), `shapes` or `model`, and written into the SPEC's Brief as a `3D scene:` line so the builder knows. It is a **feature** like any other: it gets its `feature-3d-scene` diagram before it is built (`spec-format.md`) and its end-to-end test (`verification.md` B).

## A. Two ways to make the scene
- **`shapes` — built in code from a photo (the default way; nothing to install).** The user supplies clear photos they own. The build (1) lists every visible part in 6–8 sections with shape, colour, material and relative size; (2) builds each part from simple shapes in code — no image textures — keeping each section a separate object; (3) **matches it**: a screenshot of the model beside the photo, the five biggest differences fixed, repeated up to three times; (4) adds one interaction — drag to rotate, and a "take it apart" control that moves each section out along its own axis with a thin label, and back. Best for products with clean, hard surfaces; a soft or organic product will look approximate, and the plan says so.
- **`model` — a real 3D file.** A GLB/glTF the user owns or is licensed to use (or one made in Blender on the Code machine — the free `blender-skills` pack, MIT, is installed there from its own repository with `/pf-setup options`, reviewed before installing like any third-party plugin, never bundled). Compressed — Meshopt preferred, because its decoder is tiny; Draco's decoder is a separate download that counts toward the limit in B2 — textures no larger than 1024 px, the file **≤ 1.5 MB**; a larger one is reduced or the scene falls back to `shapes`.

## B. What it must not cost (this is where 3D usually breaks a site)
1. **The page loads without it.** The first paint is a still image of the scene — a real `<img>` with dimensions, which is the page's LCP element. The 3D library and the scene load only after that, **on interaction or when the block is in view and the browser is idle** (`performance-budget.md` rule 5).
2. **The 3D code is its own chunk**, imported dynamically, an npm dependency pinned to an exact version (never a script tag to a CDN at runtime). It is **not** part of the route's first-load JavaScript, and the chunk itself is **≤ 250 KB gzipped** including the library and any decoder — tree-shaken imports only. The route's own 200 KB budget is unchanged and still measured without it.
3. **One canvas, capped** exactly as `design-standard.md` says for any canvas (device-pixel-ratio cap, size cap). Rendering stops when the block is off screen or the tab is hidden; nothing spins forever by default.
4. **It degrades cleanly.** No WebGL, a low-memory device, `prefers-reduced-motion`, or a failed load → the still image stays, with the same content beside it. This is the feature's **failure path**, and it is drawn in the diagram and tested.
5. **The content is HTML, not pixels.** The product name, every specification and every label a visitor or a search engine needs is real text beside the canvas (`seo-ai-visibility.md`); the canvas has a text alternative; rotate and take-apart are reachable by keyboard and have visible focus (`design-standard.md`).
6. **No invented facts.** Specifications shown next to the scene come from the Brief, never from the model's guess; a number the user has not supplied is left out.

## C. Checks (the builder's gate)
The performance budget is met on the page **with the block present** (LCP is the still image; no layout shift when the scene replaces it); the 3D chunk is absent from first load and ≤ 250 KB gzipped; a `model` file is ≤ 1.5 MB; the fallback renders with WebGL disabled and with reduced motion; the screenshot baseline (`verification.md` F) covers the **still-image state** and masks the live canvas, which is not pixel-stable; keyboard reaches every control. Because the live canvas is masked, an update to the 3D library is the one change the baseline cannot see: after it, the PM looks at the scene itself in the design check before approving. Any miss → `failures: scene-3d: <check>`. The result carries `scene_3d: <shapes|model>, chunk <n> KB, fallback ok`.

## Never
- Add a 3D scene to a project that did not choose it, or load it before the page is usable.
- Use a model, photo or texture the user does not own or have a licence for.
- Ship a scene that fails the performance budget "because it looks good" — the option is dropped back to the still image instead.
